# Suite audit: swag-labs-test-automation

Date: 2026-11-23. Stack: web (ts-playwright, Chromium only, root `e2e/`). 31 tests: 29 designed plus 2 session setup (`auth.setup.ts`). 0 skipped, 0 retries. Local run (`npx playwright test`, no SEED set): 45.0 s, 21 passed, 10 failed, all 10 failures are `problem_user` tests tagged with known BUGs. CI: 8 of 8 runs red (`gh run list`), but in the latest run (45202304008) 3 of 5 matrix jobs were green (all standard_user jobs and smoke locked_out_user).

This is a second, independent audit. It differs from `qa/audit/2026-11-23.md` on three facts, see "Differences from the earlier audit".

`qa-policy --stack web`: no violations (no sleeps, no positional locators, no conditional assertions). It does not catch finding 2, which is a missing `await`.

## The short version

The suite is fast, readable and free of sleeps and retries, and every test traces to a design row. The one thing to fix first is the red-on-purpose `problem_user` jobs: they make every CI run red, so nobody can read a red run as "something new broke". The `standard_user` jobs are green today and are a usable release signal for the happy path; the `problem_user` jobs are a bug report, not a gate. Second, one test (`catalog.spec.ts:18-32`) uses `expect.soft` without `await`, so its checks may never run. Not run: a fresh clone from scratch (CI does a clean `npm ci` and install on every run, which covers most of it).

## Differences from the earlier audit (`qa/audit/2026-11-23.md`)

Checked directly against the repo today:

- That audit says CI uses `continue-on-error` and a final `exit 1`. The current `e2e.yml` has neither; the matrix runs one job per suite and user, with `fail-fast: false`. Standard_user jobs are green.
- It says `smoke` and `npm test` use a random seed. `scripts/run.js:28` sets `SEED: "9"` for every npm script. Only the bare Playwright command is unseeded.
- It says 27 tests and 2 standard_user failures. The suite has 31 tests and the standard_user tests pass here.
- It missed the un-awaited soft assertions (finding 2) and scores area 4 as "4".

## What is good

- No sleeps, no retries, no `try` around locators. Waiting is done by web-first assertions.
- Page objects exposed as fixtures; `data-test` ids via `testIdAttribute`; locators live in `pages/`, not in specs.
- `seedCart` seeds local storage so a catalog bug cannot break the Given of a cart or checkout test (`fixtures/index.ts:58-72`). Keep this.
- Saved login session reused read-only, one context per test.
- Failure messages are named (`expect(locator, "label")`), so a red test says what failed.
- Seeded randomness with the seed attached to every test, and CI matrix per suite and user, so user-specific bugs show as a difference between jobs.
- Known bugs are left red with `@BUG-nn` tags instead of `skip` or `test.fail`, which keeps the bugs visible. Fix the gate (finding 1), not this.
- The design file lists what is deliberately not covered.

## Coverage gaps

Against `qa/design/swag-labs.md` (the only requirement-derived document in the repo; `docs/requirements/` is absent):

- T11 (PDF): file name and non-zero size only; content is manual by decision. Not covered for `problem_user` (blocked by BUG-02).
- T13 (empty cart cannot start checkout): the oracle is unconfirmed (swag-labs.md "Blocked / open"); runs for `problem_user` only, so `standard_user` empty-cart behaviour is untested.
- T4 (username with spaces): `problem_user` only.
- T5 (catalog fields): see finding 2, covered on paper.
- Not tested anywhere, and not listed in "Not covering": logout, the menu "Reset App State" and "About" links, the cart badge after reload or relogin, checkout overview totals (item total, tax, total), cancel buttons in checkout, direct URL access without login for pages other than `inventory.html`, error handling of the checkout info fields beyond emptiness. Add them to the design as either tests or deliberate exclusions.
- BUG-10 (images) stays manual by decision; fine, but then the image assertion at `catalog.spec.ts:19` should not claim to cover it.

## Suggested order

1. Fix finding 2 (add four `await`s). Minutes of work, and it tells you whether T5 was ever checking. Do it before trusting any green.
2. Fix finding 1 (expected-red allow-list in CI). It is the thing that turns "red is normal" into "red means new".
3. Finding 3 then 4: put requirements in the repo and set `fullyParallel`. Both cost under an hour and make the next audit comparable. Leave finding 5 alone.

Not checked: fresh local clone, per-test timing of the slowest tests (the whole run is 45 s), per-test flake rate (CI history is 8 runs and every one has red problem_user jobs, so no flake signal separable from defects).

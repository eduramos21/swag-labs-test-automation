## The short version

The suite is fast (under a minute), has no sleeps or retries, reads as Given/When/Then and uses one pattern throughout. The standard_user jobs are green and are a usable release signal for the happy path. Fix first: CI is red on every run because of the `problem_user` jobs, so a new failure in those flows is invisible, and one of the ten reds (checkout field validation) has no BUG tag, so it is not even a recorded known bug. The suite can be trusted as a release signal for standard_user today and not for problem_user, which is a bug report by design. Not run: a fresh clone from scratch.

## What is good

- No sleeps, no retries, no `try` around locators. Waiting is web-first assertions only.
- The soft-assert fix landed and is applied everywhere: all `expect.soft` calls are awaited.
- Page objects exposed as fixtures; `data-test` ids through `testIdAttribute` (`playwright.config.ts:31`); locators live in `pages/`, not in specs.
- `seedCart` (`fixtures/index.ts:55-69`) seeds the cart below the UI so a catalog bug cannot break the Given of a cart or checkout test. Keep it.
- Session reused read-only, one context per test, no order dependence.
- Named assertions (`expect(locator, "label")`), so a red test says what failed.
- Seeded randomness with the seed attached to every test, and a CI matrix per suite and user, so user-specific bugs show as a difference between jobs.
- `check:tags` fails the build when a test lacks exactly one user tag (`scripts/check-tags.js`, CI step in `e2e.yml`), so a test cannot silently drop out of a per-user run.
- Known bugs stay red with `@BUG-nn` tags instead of `skip` or `test.fail`, by decision. Fix the gate (finding 1), not this.
- The locked-out login test runs under `@smoke` only, by decision, with the reason written in the design.

## Coverage gaps

Against `docs/requirements/2- Test Cases - Product Coverage.md`. Scenarios not listed here have a test for the users in scope.

- Login, "A username with extra spaces still logs in": tested for problem_user only (`login.spec.ts:77-89`). The requirement says any user. Standard_user is untested.
- Checkout, "not allowed with an empty cart": problem_user only, provisional oracle (finding 3 and 4).
- Generate PDF order, "a PDF with the order information is downloaded": file name and size only. Content is not checked (`checkout.spec.ts:65-71`). Blocked for problem_user by BUG-02.
- Product display, "every product shows an image": the check passes for problem_user although images are a known bug (BUG-10, manual by decision), so it does not cover the image part of the requirement for that user.
- Product display, "detail page shows that same product": only the name is compared (`catalog.spec.ts:49-51`), not price, description or image.
- Checkout, "information requires every field": postal code step fails for problem_user with no recorded bug (finding 2).
- Locked-out login, "products page can't be reached" and wrong credentials: covered. Locked-out is smoke only by decision, so it is not in the regression suite.
- Not in the requirements file and not tested: logout, menu links, cart badge after reload, checkout totals (item total, tax, total), checkout cancel buttons. Add them to the design as tests or as listed exclusions.

## Suggested order

1. Finding 2: reproduce the postal-code failure and tag it or fix it. Minutes of work, and it makes the claim "every red is a known bug" true, which finding 1 needs.
2. Finding 1: expected-failures gate in CI. It turns "red is normal" into "red means something new". Do it second because it depends on the list being complete.
3. Finding 3: decide and record the empty-cart oracle for standard_user (and extend the same decision to the spaces-in-username test). It is a decision more than code and it closes the biggest gap against the requirements file. Then finding 5 (one line) when convenient. Leave finding 8 alone.

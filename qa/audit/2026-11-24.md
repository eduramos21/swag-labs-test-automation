# Suite audit: swag-labs-test-automation

Date: 2026-11-24. Stack: web (ts-playwright, Chromium, root `e2e/`). 73 tests per `npm test` (68 tests plus 5 login-setup tests; README.md "Run tests"), 0 skipped (`grep -rn "test.skip\|fixme" e2e/tests` is empty). Local full run: 1.1 min, 53 passed, 20 failed. CI: 13 consecutive green runs on 2026-11-24 (`gh run list`), 7 red before that.

## The short version

This is a clean, fast, readable suite: no sleeps, no retries, one test shape, every test traced to a requirement scenario. The problem has moved since the 2026-11-23 audit. CI is now green, but it is green because the `problem_user` jobs are exempt from failing (`continue-on-error`) and because three of the six users are never run in CI. A new regression for `problem_user` cannot turn CI red, and 20 tests are red locally that CI never shows. Fix first: make CI report unexpected failures for every user, not a blanket exemption. As a release signal it is trustworthy for `standard_user` and `locked_out_user`. It is not trustworthy for the other four users.

## What is good

- Speed and waiting: 1.1 min, no sleeps, no retries, no `try` around locators. Do not add retries. Keep it this way.
- `seedCart` writes the cart straight to storage (`fixtures/index.ts:56-64`), so a catalog bug cannot break the Given step and the failure points at the thing under test. Keep it.
- Session reuse through `auth.setup.ts` and the `setup` project dependency (`playwright.config.ts:35-40`), with `login.spec.ts` alone using the form.
- Known defects are real failing tests that assert the intended behaviour, tagged `@BUG-xx`, with a table in README.md "Red on purpose". This is the right design; the gap is how CI reads it (finding 1).
- Seeded random product picks, with the seed attached to every test (`fixtures/index.ts:88-99`) and pinned to 9 by default in `scripts/run.js`. Reproducible and still varied.
- Assertion messages name the thing checked (for example `${name} in the cart`), so failures read without opening the trace.
- `check-tags` in CI makes sure each test has one user tag. A cheap guard that most suites lack.
- README gets a stranger to a first run in six steps.

## Coverage gaps

Against `docs/requirements/2- Test Cases - Product Coverage.md` and `3- Bug Report.md`:

- Checkout empty cart: scenario exists, test runs for `problem_user` only; BUG-01 was found on `standard_user` (finding 3).
- Login with spaces around username: scenario exists, test runs for `problem_user` only; BUG-15 affects all users (finding 4).
- Checkout information accepted and Finish order: covered, but the overview totals (price, tax, total) are not asserted (finding 5).
- BUG-10 (same image on all products), BUG-11 (catalog 5 s load), BUG-12 to BUG-14 (`error_user` finish, add and remove errors): no automated test (`qa/opportunities.md:101`, D2). The catalog image check (`catalog.spec.ts:19`) only asserts the image is visible, so BUG-10 passes it.
- Not in the requirements and not tested: logout, direct URL access without a session (only `locked_out_user` is checked, `login.spec.ts:35-41`), cart persistence across reload, checkout Cancel and Back Home buttons, cart state after an order.

## Suggested order

1. Finding 1: make CI report unexpected failures for all six users instead of exempting `problem_user`. Everything else is worth less while a green build can hide regressions. Keep the tests unchanged (no skip, no `test.fail`).
2. Finding 2, then finding 3 and 4: two one-line timeout and loop changes. Do the timeout before step 1 lands in CI for `performance_glitch_user`, or it will start red on a non-defect.
3. Finding 5: the totals assertion. It covers the money path, which no test touches today.

Not checked: a fresh-clone install (I ran from the existing checkout with `.env` present), per-test CI failure rates (13 greens, but masked), and flake over repeated runs (`--repeat-each` not run).
